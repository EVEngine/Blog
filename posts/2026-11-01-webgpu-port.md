# 把 Vulkan 引擎搬进浏览器：WebGPU 移植真正难在哪里？

一套桌面渲染器迁移到 WebGPU，最先看到的成果往往是三角形出现在网页里。但从“能画出来”到“同一个游戏可以放心发布”，中间还有很长一段工程距离。

在 EVEngine 的双后端实现中，更有价值的问题是：同一份游戏脚本、同一个材质参数，在 Vulkan 和 WebGPU 上是否表达同样的意思？透明度、阴影、资源更新和错误处理，只要有一处悄悄变了，游戏作者就要承担后端差异。

这篇从项目现有实现出发，拆解这种迁移的设计方法。文中的源码依据是 EVEngine 提交 `1eb8b41028b4a294b9893e8f8a9edd80b770f303`；文档里的历史测试记录与本文新做的实测分开看，本文没有重新执行完整 GPU 测试。

## 第一关：统一行为契约

WebGPU 提供渲染与计算接口，但它的资源绑定、能力限制和校验方式有自己的约束。不能把 Vulkan 调用逐条替换，就默认完成移植。

可以先把对齐工作拆成三层：

- API 行为：合法调用产生预期结果，非法输入明确失败，资源生命周期一致。
- 渲染语义：几何覆盖、深度、混合、材质开关和阴影响应一致。
- 图像结果：确定场景使用明确的误差范围比较，而非默认所有驱动必须逐像素相同。

例如，游戏把阴影强度设成 0、0.5、1，两个后端都应该产生相应变化。只验证“画面里有阴影”，不足以证明参数生效。

这种拆分也帮助定位问题：API 成功而图像不变，可能是参数没有传到正确的着色器；几何都对而透明度不对，则应先查混合状态和深度写入。

## 着色器要保持语义，资源布局要明确

EVEngine 的 Vulkan 路径使用 SPIR-V 等资产，浏览器 WebGPU 路径使用 WGSL。自定义 shader 必须遵守各自的语言契约；不支持的输入应该明确拒绝。

危险的兼容策略，是用户提交了自定义 shader，后端却悄悄换成内置版本。程序没有报错，画面甚至还挺正常，但作者写的效果根本没运行。

另一类问题出在 CPU 与 GPU 的数据布局。材质参数在 C++ 中排列正确，不代表上传后的字节天然符合 WGSL 的对齐要求。实际工程需要核对字段偏移、缓冲区范围和动态 offset，并把这些约定固定下来。

项目现有设计中，原生 WGSL 后处理逐步消费同一套 GBuffer 语义。法线、深度和反照率的约定保持一致，SSAO、SSR 等下游效果才有可靠输入。这里最容易低估的是深度：非线性深度和线性深度一旦混用，某些视角下还能“看起来差不多”，换个相机距离就暴露问题。

## 缓存正确性，比缓存命中率更早

资源绑定缓存可以减少重复工作，但缓存 key 必须覆盖真正影响绑定的身份。

EVEngine 的历史移植记录中，有一项修复涉及多帧在途的 uniform buffer：缓存忽略了当前帧槽位的缓冲区身份，绑定组可能继续引用另一帧的 uniform arena。单帧测试很难发现这种错误，运行一段时间才可能出现材质或矩阵异常。

审查缓存时，可以逐项追问：它绑定的是哪个 buffer、哪个区间、哪张纹理和哪个 sampler？尺寸变化或资源重建后，旧缓存是否仍然有效？

同样，动态网格更新不能只测第一次上传。容量增长、索引保留、索引格式变化、非法索引拒绝，都属于公开 API 的行为，而非内部小细节。

## 有图，也要知道图证明了什么

桌面 Dawn 测试能提前发现大量问题，但它不能替代浏览器验收。

浏览器发布还包含 WebAssembly 加载、资源路径、字体图集、页面尺寸变化以及用户交互后的运行状态。一个网页只要不是黑屏，仍然可能没有正确渲染透明材质或某个后处理。

更有效的验收场景，是为每种语义设计一个小实验：半透明物体交叠验证混合与深度；遮挡物验证阴影开关；不同粗糙度验证材质响应；动态网格验证更新；窗口缩放验证目标重建。把输入、相机和随机种子固定，差异才容易解释。

原生双后端测试、真实浏览器测试、目标设备性能测试分别回答不同问题。通过其中一层，不宜把其余两层一并写成完成。

## 独立游戏开发者能得到什么

浏览器版本降低了试玩门槛：一个链接比让玩家下载压缩包更容易开始。但它也要求开发者认真处理首次加载、素材体积、设备能力探测和失败提示。

对引擎作者而言，WebGPU 移植还迫使接口变得更诚实：能力有限就返回明确错误，后端有差异就公开约定，效果支持就拿语义测试证明。这样的工程纪律，同样会改善桌面版本。

如果准备迁移自己的渲染器，可以先选一个包含模型、透明物体、阴影和后处理的小场景，写出可检查的行为，再逐项补齐。完成这个场景的闭环，比堆出很长的功能列表更能说明移植质量。
